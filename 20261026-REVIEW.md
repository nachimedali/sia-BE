# sia-BE — Code Review
2026.10.26

**Scope and method.** Static read of the code (Django 5 / DRF / simplejwt / Celery / Stripe / Zernio, ~90k lines Python, 200 test files). The Python environment was not set up and nothing was executed, so tests, ruff, mypy and `pip-audit` were **not run** and their status is unverified. Read in depth: `config/settings/*`, `config/urls.py`, `common/{ratelimit,throttling,workspaces,tokens,encryption}.py`, `accounts/views.py` and `services/auth.py`, `billing/services/{webhooks,ledger,reconciliation}.py`, the Stripe gateways, `analytics/webhooks.py`, `brand/fetching.py`, `content/services/media.py`, `collaboration/views.py` (public review views), `config/celery.py`. Not reviewed: most domain logic (content, planning, taste, trends, learn, tools, scheduling), the migrations and the individual viewsets' permission classes. The findings below are read from the code, not reproduced.

## Verdict

Better engineered than most codebases of this size. The strong points are the tenancy resolver (404, never 403), the append-only credit ledger with a row lock and nightly drift reconciliation, hashed single-use link tokens, a webhook-first billing model with replay protection, and SSRF guards on the site crawler. The weak points are operational: production safety depends on settings that are not pinned, nothing declares or locks the dependencies, and the session and rate-limit story has gaps.

## Critical / High

### 1. Production can boot with the fake billing gateway, whose webhook secret is public
- `prod.py` pins `USE_FAKE_PLATFORM_ADAPTER`, `USE_FAKE_AI_PROVIDERS`, `USE_FAKE_MEDIA_EDITOR`, `USE_FAKE_TREND_VENDORS` and `USE_FAKE_STORAGE` to off, and requires `ZERNIO_API_KEY`. It does **not** pin `USE_FAKE_BILLING`.
- `base.py:430` defaults `USE_FAKE_BILLING = not STRIPE_SECRET_KEY`, and `STRIPE_WEBHOOK_SECRET` defaults to `""`. A production deploy that lost `STRIPE_SECRET_KEY` boots with no error.
- The fake gateway's `verify_webhook` (`billing/gateways/fake.py:76-84`) accepts anything HMAC-signed with the hard-coded `"whsec_fake"`. Anyone who reads the repo can forge `customer.subscription.*` / `invoice.payment_succeeded` events, which the webhook treats as the source of truth. That is a free plan upgrade and free credits.
- The same pattern applies to `USE_FAKE_SITE_FETCHER` (default True) and `USE_FAKE_REPORT_RENDERER` (default True), which `prod.py` also leaves unpinned.
- **Fix:** in `prod.py`, set all three fakes to False and read `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` without defaults, as is already done for `ZERNIO_API_KEY`.

### 2. `httpx` is imported in 7 modules but declared nowhere
- `httpx` is imported in `brand/fetching.py`, `trends/providers/http.py`, `ai/providers/{nanobanana_image,llm_text,embeddings}.py`, `analytics/providers/zernio.py` and `channels/adapters/zernio.py`.
- `requirements.txt` and `requirements-dev.txt` do not list it. It may arrive transitively, but `requirements.txt` itself argues against relying on that (see the `python-dateutil` and `tzdata` comments).
- If it is not present, the real AI providers, the Zernio adapters and the crawler fail with `ImportError` in production. The fakes mask this in dev and test.
- **Fix:** declare it.

### 3. No dependency pinning, lockfile or build artifacts
- Every production dependency is unpinned (`django>=5.0,<6`, `celery>=5.4`, `stripe`, `pillow`, and others have no or loose bounds). There is no lockfile, Dockerfile or CI configuration in the repo.
- A fresh install can silently pick up a new `stripe`, `pillow` or `simplejwt` major, with no reproducibility and no audit trail.
- **Fix:** pin with `pip-compile` or `uv`, run `pip-audit` in CI, and commit the lockfile.

### 4. Password reset does not revoke existing sessions
- `confirm_password_reset` (`accounts/services/auth.py:99-114`) sets the password and saves. It does not blacklist outstanding refresh tokens, although the `token_blacklist` app is installed.
- A stolen refresh token survives the reset for up to 14 days, and rotation keeps it alive indefinitely. The reset is the user's remedy for a compromised account, and it does not remove the attacker.
- **Fix:** blacklist all `OutstandingToken` rows for the user on reset (and on any password change).

### 5. Rate limiting trusts a client-controlled header and has no per-account limit
- `client_ip` (`common/throttling.py`) uses the **left-most** `X-Forwarded-For` entry. The docstring says this is correct only behind a proxy that overwrites the header. Most load balancers (ALB, nginx `$proxy_add_x_forwarded_for`) append instead, so the left-most entry is attacker-supplied. Rotating that header bypasses the login, register and reset buckets entirely.
- Buckets are per IP only. A distributed attack on one account, or on the unauthenticated review and report tokens, is not limited by account.
- If Redis is unreachable, `TokenBucket.consume` raises inside the throttle and the request fails with a 500. The publishing limiter has a Postgres fallback; the auth limiter has none.
- **Fix:** take the right-most trusted hop (or configure a trusted proxy count), add a per-email login bucket, and decide explicitly between fail-open and fail-closed.

### 6. Stripe webhook failures are swallowed and never retried
- `process_event` (`billing/services/webhooks.py`) records the event row first, and if the handler raises, stores the error and returns `True` (HTTP 200). Stripe never retries, and the stored `event_id` makes a replay a no-op.
- A transient DB or lock error on `invoice.payment_succeeded` means the customer paid and does not get the plan or credits. Recovery is manual, and the code comment names the log and the row as "what an operator replays from".
- Nothing here replays failed rows automatically. The nightly reconciliation checks ledger drift only.
- Ordering is also not handled: Stripe does not order deliveries, so a stale `customer.subscription.updated` can overwrite newer state unless the handler compares timestamps.
- **Fix:** return 5xx (or run a periodic job that retries rows with `error` set), and guard subscription updates against stale events.

## Medium

- **`SECRET_KEY` and `FIELD_ENCRYPTION_KEY` are not validated in production.** `.env.example` ships `SECRET_KEY=change-me`. `Fernet` rejects a bad encryption key, but nothing rejects a weak `SECRET_KEY`, and `SIGNING_KEY = SECRET_KEY` means a placeholder value makes JWTs forgeable. Fail at boot on known placeholders and short values.
- **Video upload type is client-declared.** `_sniff_content_type` (`content/services/media.py:58`) returns the declared `Content-Type` first, then the file extension. Videos are never opened or checked against magic bytes (images are, via Pillow). Arbitrary bytes labelled `video/mp4` are stored and later served, and a malformed file reaches whatever transcodes it downstream.
- **No key rotation for field encryption.** `get_fernet` builds a single `Fernet`, not `MultiFernet`, so rotating `FIELD_ENCRYPTION_KEY` makes every existing value raise `ValueError` on read. The field is not used for platform tokens in v1, but the module's stated purpose is to avoid a painful retrofit.
- **SSRF guard has a DNS-rebinding window.** `assert_public_url` resolves the host, then `httpx` resolves it again on connect. A hostile DNS server can answer public the first time and `127.0.0.1` the second. Redirects are re-checked and ports are restricted, which helps. The fix is to connect to the vetted IP (custom transport) or pin resolution.
- **Registration is an email-enumeration oracle.** `RegisterSerializer` returns "An account with this email already exists", while password reset deliberately always returns 202. The register throttle is the only mitigation, and it is the bypassable per-IP one (see item 5).
- **Celery with `acks_late` and the Redis broker has no `visibility_timeout`.** The default is one hour. `config/celery.py` says `analyze_q` jobs can run "minutes to hours", so long tasks get redelivered and run twice unless they are idempotent. The default queue is named `"default"` but is not in `task_queues`, so an unrouted task lands on a queue no worker consumes.
- **Django admin is mounted at `/admin/`** with no extra restriction in the code (IP allowlist, separate host, or 2FA). Fine if the edge restricts it; confirm.
- **No global DRF throttling.** Only auth and the public token views are throttled. Authenticated endpoints that spend money (AI generation, video renders, tools) rely on the credit ledger alone, with no request-rate limit, so a runaway client can queue provider calls up to its balance.

## Hygiene / maintainability

- `ai/creative_seed.py` is 1,444 lines, and `content/views.py` is 1,043 lines. Several models and services exceed 600 lines.
- The seed migrations (`SEED_CATALOG_ON_MIGRATE` defaults to True) write catalogue data from `migrate`. The comment says "never a production switch", but nothing enforces that in `prod.py`.
- `csrf_exempt` is applied on the webhook `post` methods inside a DRF `APIView`; DRF's `APIView.as_view()` is already csrf-exempt, so the decorators are redundant and imply a protection that is not there. Keep the signature check as the real control.
- `ThrottledTokenObtainPairView` returns tokens in the response body, as designed for the BFF. If the Advanced-tier direct API access (`base.py` CORS comment) is ever exposed to browsers, that design changes.
- `CORS_ALLOW_CREDENTIALS = True` with `CSRF_TRUSTED_ORIGINS = CORS_ALLOWED_ORIGINS`: harmless with bearer auth, but the setting implies cookie auth that does not exist. Remove it unless needed.
- `UPDATE_LAST_LOGIN = True` writes to the users table on every token obtain.
- Balance is `SUM(delta)` over the whole ledger on every debit. It is correct and locked, but O(history) per spend; add a periodic checkpoint if ledgers grow.

## Strengths

- Tenancy: one resolver (`request_workspace`), a 404 for another tenant's workspace, an explicit workspace header (no silent fallback), and a test that walks `router.registry` to sweep every viewset.
- Billing: webhook as source of truth, signature verified before parsing, events recorded by id (replay-safe), append-only ledgers with compensating refund rows, `select_for_update` on the workspace, and a nightly drift report that never repairs.
- Tokens: `secrets.token_urlsafe(32)`, only the SHA-256 digest at rest, constant-time comparison, single-use approval links, and 404 (not 403) to avoid existence leaks.
- Webhook signature checks use `hmac.compare_digest`; the Zernio webhook refuses all deliveries when its secret is unset.
- Production settings are hardened: HSTS with preload, secure cookies, `X_FRAME_OPTIONS=DENY`, referrer policy, most fakes pinned off, and a comment explaining why.
- SSRF guard checks scheme, port, credentials, literal and resolved IPs on every redirect hop, with a size cap and robots.txt support.
- Encrypted fields store ciphertext (asserted by a test), and uploads are size-limited (50 MB) with image integrity probing.
- `.env*` is git-ignored, only `.env.example` is committed, and I found no committed secret files in history (filename check only, not a content scan).
- Rate limiter design (atomic Lua token bucket, Postgres fallback for publishing) is thoughtful, and error responses go through one envelope.

## Suggested order of work

1. Pin the remaining fakes off in `prod.py` and require the Stripe keys (item 1).
2. Declare `httpx`, pin and lock all dependencies, add `pip-audit` (items 2 and 3).
3. Blacklist refresh tokens on password reset (item 4).
4. Fix the client-IP trust and add a per-account login limit (item 5).
5. Make Stripe webhook failures retryable and order-safe (item 6).
6. Validate `SECRET_KEY` at boot, check video magic bytes, set the Celery visibility timeout, and use `MultiFernet`.
